### Почему планирование не пропустили

`docs/POST_MVP_PLAN.md` §1 — четыре строчки требований, никакой детализации уровня
`TECHNICAL_PLAN.md` для Этапов 1-6. Реальный design gap: `useEffect` — вторая durable-cell
на fiber (после `useState`), и чекпоинт Этапа 6 прямо предупреждал не считать
write-дисциплину `HookSnapshot`/`commitFiberHooks` автоматически безопасной для новых
хуков. План закрыл 7 архитектурных развилок: единый hook-list с дискриминацией по `kind`
(не два параллельных списка — иначе call-order индексы разъедутся при чередовании
`useState`/`useEffect`), write-дисциплина snapshot-in-render/finalize-in-commit для
эффектов, сравнение deps (`Object.is`, семантика `undefined`/`[]`), точка запуска
passive-фазы, порядок выполнения эффектов и cleanup, cleanup при DELETION, точки вызова.

## Находка основной сессии — до передачи плана кодеру

При проверке готового плана (Opus) я сам проследил Развилку 4 («passive-эффекты
синхронно внутри `commitRoot`») и нашёл реентрантный баг **до** отправки плана в кодинг:
`setState` внутри эффекта, вызванного изнутри `commitRoot`, синхронно перезапускает
`scheduleWork`/`workLoop`; если этот вложенный рендер завершается **до** возврата из
внешнего `commitWip`, а `commitWip` продолжает выполняться ПОСЛЕ `commitRoot` (промоушен
`current*`), — внешний хвост `commitWip` затирает уже корректно промотированные
`current*` от вложенного коммита. План изначально документировал это как «известное
ограничение — setState на первом mount теряется»; я переформулировал Развилку 4:
`commitRoot` возвращает `PendingEffect[]` вместо самостоятельного запуска, а
`runPassiveEffects` переносится в `commitWip`, строго ПОСЛЕ промоушена `current*` —
трёхстрочная правка `scheduler.ts`. Это не только устранило реентрантный баг, но и
избавило от «техдолга по первому mount» — он перестал существовать как класс.

## Находка независимого ревью — реентрантность на уровне `workLoop`

Правка Развилки 4 устранила клоббер ВНУТРИ `commitWip`, но не учла, что вызывающий
`workLoop` имеет свой код ПОСЛЕ `commitWip()`:

```
commitWip();
if (startNextPendingRender()) {   // ← безусловно, до фикса
  workLoop();
}
```

Если эффект вызывает `setState`, реентрантный `scheduleWork` синхронно стартует
вложенный `workLoop` (idle-ветка, `nextUnitOfWork === null` на момент вызова). Если
ЭТОТ вложенный рендер не укладывается в бюджет и уступает (`shouldYield`), он оставляет
`nextUnitOfWork`/`wipRoot`/`wipContainer`/`wipVNode` указывающими на своё приостановленное
состояние с уже запланированным тиком. Управление разматывается назад во ВНЕШНИЙ
`workLoop`, который безусловно вызывал `startNextPendingRender()` — и если в очереди
`pending` оставалась запись, перезаписывал те же модульные переменные, осиротив
вложенный рендер. Его отложенный тик потом резюмировал уже чужое состояние.

Ревьюер воспроизвёл детерминированным тестом (два контейнера, шагающие часы, вложенный
рендер намеренно растянут за бюджет тиком другого контейнера): контейнер A терял
рендер (застревал на mount-версии), контейнер B получал задвоенный узел.

**Фикс** — точный `file:line`, однострочная правка (`scheduler.ts`, `workLoop`):

```diff
-  if (startNextPendingRender()) {
+  if (nextUnitOfWork === null && startNextPendingRender()) {
     workLoop();
   }
```

Guard безопасен и не создаёт нового пропуска дренажа: `nextUnitOfWork !== null` на этой
строке возможен **только** через путь yield-with-tick, то есть тик на возобновление уже
гарантированно запланирован — вложенный рендер сам доведёт себя до `commitWip()` и сам
выполнит дренаж очереди на своём уровне стека. Регресс-тест (`hooks.test.ts`, кейс
«реентрантный setState-в-эффекте не затирает приостановленный вложенный рендер»)
экспериментально проверен ревьюером через откат фикса — падает без него.

### Побочная находка при написании регресс-теста — НЕ чинили

При проектировании двухконтейнерного регресс-теста контейнер B после фикса продолжал
получать задвоенный узел (хотя контейнер A переставал терять рендер — то, что чинит
фикс). Расследование (синтетический тест на `master`, три `scheduleWork` без единого
хука/эффекта) подтвердило: это **отдельная, до-существующая находка Stage 5**, уже
документированная в самом коде (`scheduler.ts`, докблок `scheduleRerender`: «the
scheduler keeps ONE current triple, a Stage 5 limitation»). `currentContainer`/
`currentRoot`/`currentVNode` — одна глобальная тройка, не per-контейнер `Map`; апдейт
контейнера, не являющегося «последним закоммиченным глобально», всегда идёт как чистый
remount, а не diff. Не относится к useEffect и не в объёме этого плана — не чинили.
Assertion на containerB в регресс-тесте ослаблена до проверки факта выполнения апдейта
(`toContain`), а не формы итогового DOM, с комментарием, объясняющим почему.

**Итог: 106/106 тестов зелёные** (105 после кодинга + 1 регресс-тест реентрантности),
множественные прогоны без флейка, `tsc --noEmit` чисто.

## Реализация: ключевые решения

- **Единый hook-list, дискриминация по `kind`.** `Hook`/`HookSnapshot` в `hooks.ts` —
  дискриминированные объединения (`"state" | "effect"`), делят один `hookIndex`.
- **Write-дисциплина эффектов зеркалит `useState`.** `useEffect` в render только снимает
  `EffectHookSnapshot` (`shouldRun`, `create`, `deps`); durable `EffectHook.deps` пишет
  только `commitFiberHooks`, durable `EffectHook.cleanup` — только `runPassiveEffects`.
- **Passive-фаза — синхронно, но НЕ внутри `commitRoot`.** `commitRoot` возвращает
  `PendingEffect[]`; `commitWip` (`scheduler.ts`) запускает `runPassiveEffects` последней
  строкой, строго после промоушена `current*` — единственная (за вычетом реентрантного
  фикса выше) правка `scheduler.ts`.
- **Cleanup при DELETION.** Новые `collectDeletionCleanups`/`collectSubtreeCleanups`
  (`fiber.ts`) обходят удаляемые поддеревья и собирают cleanup всех effect-хуков внутри —
  включая cleanup САМОГО удаляемого компонентного корня (потребовало добавить
  `hooks: prev.fiber?.hooks` в `addDeletion`, вне первоначального перечня плана, но по
  его намерению — без этого cleanup верхнего удаляемого компонента был недостижим).
- **Порядок:** `finalizeHooks` сменён на post-order (дети раньше родителя) — эффекты
  запускаются child-first, как в React; unmount-cleanup'ы идут в `pending` первыми.

## Технический долг, зафиксированный сознательно

- **Единая глобальная тройка `current*` в `scheduler.ts` (Stage 5, уже документировано
  в коде).** Апдейт контейнера, не являющегося последним закоммиченным глобально, идёт
  как remount, не diff. Раньше было достижимо только вручную чередуя `scheduleWork` на
  разные контейнеры; useEffect делает это чуть более вероятным (эффект одного контейнера
  может дёрнуть апдейт другого), но природа находки не меняется. Триггер пересмотра:
  если понадобится реальный multi-root сценарий (несколько независимых `render()` в
  демо) — потребует `Map<Element, {root, vnode}>` вместо тройки, отдельный план.
- **Passive-эффекты синхронны** (нет отдельного тика после paint, как в React) —
  осознанное упрощение под учебный масштаб (см. план, Развилка 4).
- **Cleanup при DELETION вызывается ПОСЛЕ физического удаления DOM** — cleanup не должен
  полагаться на присутствие удаляемого DOM.
- **Один проход cleanup-then-create на эффект** (не два раздельных прохода как в React).
- **`hasComponentDescendant` O(n²)** — перенесённый из чекпоинта Этапа 6, не тронут.
