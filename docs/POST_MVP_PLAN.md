# POST_MVP_PLAN — vdom-fiber

Расширения после того, как MVP (Этапы 0–6) закрыт и демо-счётчик работает end-to-end
через собственный VDOM + Fiber + scheduler + hooks. Порядок — ориентировочный,
берётся по интересу и сложности.

## 1. `useEffect` (готово)

- Хук с массивом зависимостей; эффекты запускаются **после** commit-фазы.
- Cleanup-функция вызывается перед повторным запуском эффекта и при размонтировании.
- Требует: список эффектов на fiber, сравнение deps, фаза «passive effects» после commit.

Реализовано на ветке `post-mvp/use-effect`: план — `docs/plans/post-mvp-use-effect.md`,
чекпоинт — `docs/handoff/2026-08-26-post-mvp-use-effect.md`. По ходу ревью найден и
исправлен реентрантный баг планировщика (не специфичный для useEffect по сути, но
достижимый только через него) — см. чекпоинт.

---

**Планируемые секции ниже (§2–§5)** оформлены как задание для свежего кодинг-агента:
пути файлов и имена API указывают на реальную структуру `src/` (проверено при аудите).
Общий инвариант, который нельзя нарушать ни в одной секции: **render-фаза не трогает
DOM и не мутирует durable-состояние** (только снимает `hookSnapshots` на WIP-fiber);
всё durable пишется исключительно в commit/passive-фазе — это то, что делает
прерывание безопасным (см. write-дисциплину `useState`/`useEffect` в `src/hooks.ts`).

## 2. Context API

**Файлы:** новый `src/context.ts` (+ `src/context.test.ts`); правки `src/hooks.ts`
(`useContext`), `src/fiber.ts` (проброс значения при обходе компонентных fiber'ов),
`src/index.ts` (ре-экспорт). Тип контекста — в `src/context.ts`, при необходимости
`src/types.ts` для общих типов.

**Новый публичный API:**

- `createContext<T>(defaultValue: T): Context<T>` — возвращает объект контекста с
  полями `{ defaultValue: T; Provider: ComponentFunction }`. `Provider` —
  функциональный компонент, принимающий `props.value: T` и `props.children`.
- `useContext<T>(context: Context<T>): T` — читает ближайшее вверх по дереву значение
  провайдера или `defaultValue`, если провайдера нет.

**Механизм (учёт прерываемого рендера).** Значение контекста НЕ хранить в
module-level стеке, который наполняется по ходу render-обхода: render прерываем, и
частично наполненный стек рассинхронизируется при возобновлении с середины. Вместо
этого при обработке компонентного fiber'а в `reconcileChildren` (`src/fiber.ts`,
ветка `typeof fiber.type === "function"`) пробрасывать активные значения контекстов
на сам WIP-fiber (новое поле `Fiber.contextValues?: Map<Context<unknown>, unknown>`,
копируется/дополняется от родителя — provider-fiber добавляет свою пару). `useContext`
читает `currentFiber.contextValues` (по аналогии с тем, как `useState` читает
`currentFiber`). Так значение доступно из сохранённого состояния fiber'а и не зависит
от порядка/возобновления обхода.

- Provider реализуется как обычный компонент: `Provider(props)` возвращает
  `props.children` (один VNode или, если детей несколько, требует обёртки — фрагменты
  вне скоупа §2, см. §5). Установка значения происходит в `reconcileChildren` при
  распознавании provider-типа, а не в теле `Provider`.

**Инвалидация подписчиков.** В MVP-масштабе достаточно: смена `value` у провайдера
влечёт повторный рендер поддерева через обычный планировщик (провайдер — компонент,
его re-render проходит по детям; `useContext`-потребители перечитывают
`contextValues` в своём render). Точечная инвалидация только подписчиков (в обход
рендера промежуточных компонентов) — вне скоупа §2; зафиксировать как ограничение.

**Критерии готовности (тестируемо на DOM + логгер, jsdom):**

- `useContext` без провайдера возвращает `defaultValue`.
- Значение провайдера доходит до потомка любой глубины без props-drilling; DOM
  отражает значение.
- Вложенные провайдеры одного контекста: ближайший выигрывает.
- Смена `value` провайдера через `setState` выше по дереву перерендеривает потомков,
  DOM обновляется.
- Прерывание рендера поддерева с `useContext` более приоритетным апдейтом того же
  контейнера не приводит к рассинхрону значения (потребитель вытесняющего рендера
  видит корректное значение).

**Открытые продуктовые решения (за пользователем):** нужен ли синтаксис
`Context.Provider` как отдельный компонент против функции `provide(context, value,
children)` — API-вкус, не техническая развилка.

## 3. Concurrent-фичи сверх базового планировщика

**Файлы:** `src/scheduler.ts` (батчинг, отмена устаревшего WIP, `startTransition`);
`src/hooks.ts` (`useTransition`); `src/index.ts` (ре-экспорт). Опирается на уже
существующие `Priority` (enum `Immediate`/`UserBlocking`/`Normal`/`Idle`), `pending`
(очередь `PendingUpdate[]`), preemption по `activePriority`/`wipContainer` и
`startNextPendingRender` в `src/scheduler.ts`.

**Новый публичный API:**

- `startTransition(scope: () => void): void` — на время вызова `scope` помечает все
  вызванные внутри `setState`/`scheduleWork` приоритетом `Priority.Idle` (или новым
  `Priority.Transition` между `Normal` и `Idle` — см. открытое решение). Реализация:
  module-level флаг «мы внутри transition» в `src/scheduler.ts`, который
  `scheduleRerender` читает как источник приоритета вместо дефолтного `Normal`.
- `useTransition(): [boolean, (scope: () => void) => void]` (в `src/hooks.ts`) —
  новый durable-хук `kind: "transition"` в общем hook-list; `boolean` = «есть
  незавершённый transition-рендер для этого компонента», второй элемент — обёртка над
  `startTransition`, дёргающая re-render для сброса pending-флага после коммита
  transition-рендера.

**Батчинг нескольких `setState` в один проход.** Сейчас каждый `setState` →
`scheduleRerender` → `scheduleWork` немедленно (idle-ветка запускает `workLoop`
синхронно). Батчинг: если уже идёт синхронный batch-скоуп (напр. внутри одного
обработчика события или `startTransition`), только ставить обновление в `pending` и
запускать `workLoop` один раз в конце скоупа. Реализовать через module-level
«batch depth» в `src/scheduler.ts`; дедупликация нескольких апдейтов одного
контейнера в `pending` (оставлять последний с наивысшим приоритетом).

**Отмена/перезапуск устаревшего WIP (tearing-free).** Частично уже есть: preemption
в `scheduleWork` отбрасывает WIP при более приоритетном апдейте того же контейнера.
Расширить на равноприоритетный, но более свежий апдейт того же контейнера (сейчас он
ждёт в `pending`, из-за одной глобальной `current*`-тройки это работает лишь для
одного корня — см. техдолг ниже). Гарантия: коммитится только WIP, построенный от
последнего актуального состояния; устаревший отбрасывается до commit (DOM не тронут).

**Зависимость-блокер.** Полноценный multi-root concurrent требует убрать
единственную глобальную тройку `currentContainer`/`currentRoot`/`currentVNode` в
`src/scheduler.ts` в пользу `Map<Element, {root, vnode}>` (см. «Известное ограничение»
ниже). Батчинг и `startTransition` для одного корня можно сделать и до этого; отмену
устаревшего WIP между разными корнями — только после.

**Критерии готовности (детерминированно, инъекция `now`/`scheduleTick` через
`__setSchedulerDeps`, как в `src/scheduler.test.ts`):**

- `startTransition(() => setX(...))` даёт обновлению приоритет ниже дефолтного:
  user-blocking `setState`, выпущенный во время идущего transition-рендера,
  коммитится раньше.
- Несколько `setState` в одном batch-скоупе дают ОДИН commit (счётчик рендеров = 1).
- `useTransition` возвращает `true`, пока transition-рендер не закоммичен, потом
  `false`; DOM отражает финальное состояние.
- Устаревший transition-WIP, вытесненный более свежим апдейтом того же контейнера, не
  коммитится (нет промежуточного «рваного» DOM).

**Открытые продуктовые решения:** (1) отдельный `Priority.Transition` против
переиспользования `Priority.Idle` — влияет на enum и порядок в очереди; (2) границы
авто-батчинга (только явные скоупы против всех синхронных `setState`) — продуктовое.

## 4. Полноценный JSX

**Файлы:** `tsconfig.json` (или отдельный `tsconfig` для примеров) —
`"jsx": "react-jsx"`, `"jsxImportSource": "vdom-fiber"`; новый `src/jsx-runtime.ts`
(экспорт `jsx`, `jsxs`, `Fragment`); `src/jsx-dev-runtime.ts` (dev-вариант);
опционально `src/jsx.d.ts` для `JSX.IntrinsicElements`. Пример-демо переводится на
JSX. `src/index.ts` и hyperscript-API (`h`/`createElement`) остаются рабочими без
изменений — JSX это отдельный слой поверх, не замена.

**Механизм.** Новый JSX-transform (`react-jsx`) компилирует `<div/>` в
`jsx("div", props)` / `jsxs(...)` (для статического списка детей), а НЕ в
`createElement`. Поэтому нужен `src/jsx-runtime.ts`, адаптирующий сигнатуру нового
transform (`jsx(type, props, key?)`, где children лежат в `props.children`) к
существующему `createElement(type, props, ...children)`. `Fragment` — экспортируемый
символ/функция-маркер; поскольку фрагменты (§5) в текущем ядре не поддержаны, либо
реализовать `Fragment` в паре с §5, либо на первом шаге ограничиться одним корневым
элементом и явно задокументировать, что `<>…</>` требует §5.

**Критерии готовности:**

- Файл `.tsx` с `jsxImportSource: "vdom-fiber"` компилируется `tsc --noEmit` без JSX-
  ошибок и рендерится через `scheduleWork` в тот же DOM, что и эквивалентный вызов `h`.
- `props`, обработчики (`onClick`), `key`, интерполяция текста работают идентично
  hyperscript-версии (тест: JSX и `h`-версии одного дерева дают равный `innerHTML`).
- hyperscript-API продолжает работать без сборки (существующие тесты зелёные).

**Открытые продуктовые решения:** (1) новый transform (`jsx-runtime`, без babel,
только tsc/esbuild) против babel-плагина — рекомендуется `jsx-runtime` как более
простой и без babel-зависимости; (2) поддерживать ли classic-transform
(`jsxFactory: "h"`) для совместимости — по желанию.

## 5. Прочие nice-to-have

Каждый пункт — самостоятельная мини-задача; порядок по интересу.

- **Дополнительные хуки** (`src/hooks.ts`, ре-экспорт в `src/index.ts`): `useRef`
  (durable `kind: "ref"`, объект `{ current }`, переживает рендеры через `alternate`),
  `useMemo`/`useCallback` (durable-хук с `deps` + сравнением через существующий
  `depsChanged`), `useReducer` (обобщение `useState`: тот же durable state-cell, но
  `dispatch` кладёт action, а деривация применяет `reducer`). Все встраиваются в общий
  per-fiber hook-list по call-order — новый `HookKind` на каждый. DoD: значение
  переживает re-render; `useMemo` пересчитывает только при смене deps; тесты на DOM +
  счётчик пересчётов.
- **Фрагменты** (`<>…</>`) и порталы. Фрагмент — тип VNode, прозрачный для DOM (как
  компонентный fiber: не владеет узлом, дети живут в ближайшем host-предке — механика
  `placeChildren`/`collectHostDoms` в `src/fiber.ts` уже это умеет для компонентов).
  Портал — рендер поддерева в другой контейнер. DoD: фрагмент с N детьми монтируется
  без обёртки-узла; портал помещает узлы в указанный контейнер.
- **Обработка ошибок рендера** (аналог error boundary). Требует try/catch вокруг
  вызова `fiber.type(fiber.props)` в `reconcileChildren` (`src/fiber.ts`) и поиска
  ближайшего boundary-компонента вверх по `parent`. DoD: брошенное в render компонента
  исключение перехватывается ближайшим boundary, показывается fallback, остальное
  дерево цело.
- **Дев-трейсинг единиц работы планировщика** (`src/scheduler.ts`): опциональный
  колбэк в `SchedulerDeps` (напр. `onUnitOfWork?`), вызываемый вокруг
  `performUnitOfWork` и на yield/resume/commit — визуализация «render → yield →
  resume». DoD: включаемый трейс перечисляет единицы работы и точки прерывания.
- **Мини-бенчмарк**: сравнить синхронный проход (прокрутка `performUnitOfWork` в
  `while`-цикле, как в `src/fiber.test.ts`) и прерываемый (`scheduleWork` с малым
  `frameBudgetMs`) на большом дереве; измерить максимальную непрерывную блокировку
  главного потока. DoD: скрипт печатает сравнение времён/размеров слайсов.

## Известные ограничения / техдолг (несут вперёд, не блокируют MVP)

- **Единая глобальная тройка `current*` в `src/scheduler.ts`** (`currentContainer` /
  `currentRoot` / `currentVNode`) — не per-container. Апдейт контейнера, не являющегося
  последним закоммиченным глобально, идёт как remount, а не diff. Задокументировано в
  докблоке `scheduleRerender` (`src/scheduler.ts`). Триггер пересмотра: реальный
  multi-root сценарий (несколько независимых корней) — потребует
  `Map<Element, {root, vnode}>` вместо тройки; это блокер полноценного multi-root
  concurrent (§3) и цена входа для §3 отмены устаревшего WIP между разными корнями.
- **Passive-эффекты синхронны** (нет отдельного тика после paint, как в React) — §1,
  осознанное упрощение. Триггер: мини-бенчмарк (§5) покажет блокировку отзывчивости.
- **`hasComponentDescendant` O(n²)** в `src/fiber.ts` (перенесено с Этапа 6).
- **Нет regression-теста на устойчивость реконсиляции к внешне вставленным DOM-узлам**
  (`adoptSubtreeDoms` в `src/fiber.ts` индексирует по реальному `childNodes`/`nextSibling`).
  Найдено при конкурентном исследовании: в точности такой баг был в Preact 8.0
  (`innerDiffNode`, [issue #1250](https://github.com/preactjs/preact/issues/1250)) — сторонний
  узел, вставленный в контейнер мимо рендера, удалялся при следующем диффе. Подробности и
  другие находки — [docs/research/vdom-fiber-landscape.md §1.2](research/vdom-fiber-landscape.md#12-preact--тот-же-дизайн-без-time-slicing).

## Явно вне скоупа

- SSR / гидратация.
- Синтетическая система событий уровня React (делегирование на корень).
- Совместимость с экосистемой React (это самостоятельный учебный движок, не замена React).
