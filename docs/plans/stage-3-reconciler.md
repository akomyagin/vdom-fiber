# План Этапа 3 — VDOM-диффинг (reconciliation), синхронный

Файл-исполнитель: `src/reconciler.ts` (+ `src/reconciler.test.ts`).
Первоисточник требований: `docs/TECHNICAL_PLAN.md`, раздел «Этап 3». Этот план его
уточняет и расширяет, но НЕ отменяет: перечисленные там правила диффа и тест-кейсы
входят в объём как есть.

## Цель

Реализовать синхронный диффинг двух виртуальных деревьев одного контейнера и
применить **минимальный** набор реальных DOM-мутаций in place. Повторный вызов
`reconcile(container, prev, next)` не должен перестраивать всё поддерево: узлы,
которые не изменились по типу, обязаны сохранять DOM-идентичность (тот же самый
объект `Node`, проверяемо через `===`).

## Границы (что НЕ входит в Этап 3)

Явно вне объёма — это следующие этапы, не трогать:

- **Fiber-структура данных** (`Fiber`, `alternate`, effect-tags, linked-list
  `child`/`sibling`/`return`) — Этап 4. Диффинг здесь **рекурсивный** и синхронный.
- **Прерываемость / time-slicing / `shouldYield` / `MessageChannel`** — Этап 5.
- **Приоритеты, очередь обновлений, вытеснение рендера** — Этап 5.
- **Хуки / функциональные компоненты как `type`** — Этап 6. В Этапе 3 `type` — это
  только строка (тег или `TEXT_ELEMENT`), функциональные компоненты не обрабатываются.
- **LIS-оптимизация переупорядочивания детей** — не нужна. Достаточно keyed-map +
  `insertBefore`. Минимальность мутаций здесь понимается как «не пересоздавать
  неизменённые узлы», а не «минимальное число move-операций».

Никаких правок в публичном API за пределами уже существующего ре-экспорта
`reconcile` в `src/index.ts` (он там уже есть — трогать не нужно).

## Ключевое архитектурное решение по props: обобщить `applyProps` → `patchProps`

Сейчас `applyProps(dom, props)` в `src/render.ts` умеет только **добавлять** props к
свежесозданному узлу и не хранит ссылок на навешенные обработчики. Для диффинга
существующего узла этого мало.

**Решение: ввести единую функцию `patchProps(dom, prevProps, nextProps)` и сделать её
единственным местом применения props во всём проекте.** Mount становится частным
случаем патча от пустых старых props.

Обоснование и следствия:

- **Откуда брать старые props при патче.** У `reconcile` целиком доступен
  `prev: VNode | null`, значит `prev.props` — прямой и достоверный источник старых
  props. Отдельное хранилище старых props/обработчиков на самом DOM-узле (напр.
  `dom.__props`) **не заводить**: это лишнее состояние, дублирующее то, что уже есть в
  виртуальном дереве, и оно рассинхронизируется первым же местом, где узел тронут
  мимо reconciler. Единственный источник истины — виртуальное дерево.
- **Как определять diff атрибутов/style/обработчиков.** Пройти объединение ключей
  `prevProps` и `nextProps` (кроме `children`):
  - ключ есть в `next`, нет в `prev` → **добавить**;
  - ключ есть в обоих, значение изменилось (сравнение по `!==`, ссылочное для
    функций/объектов) → **обновить** (для обычного атрибута — переустановить, для
    обработчика — снять старый и навесить новый, для `style` — см. ниже);
  - ключ есть в `prev`, нет в `next` → **удалить** (`removeAttribute` для атрибута;
    `removeEventListener` для обработчика; обнулить снятые CSS-свойства для `style`).
  - Значение не изменилось (`prev[key] === next[key]`) → **ничего не делать** (это и
    даёт минимальность мутаций для props).
- **Снятие именно того обработчика, что был навешен.** `removeEventListener` требует
  ссылку на ту же самую функцию. Она лежит в `prevProps[key]` — вызывать
  `dom.removeEventListener(eventName, prevProps[key] as EventListener)` именно с этой
  ссылкой, затем при необходимости `addEventListener(eventName, nextProps[key])`.
  Имя события выводится тем же правилом, что уже в `render.ts`: часть ключа после
  `on`, целиком в нижний регистр (`onClick` → `"click"`, `onMouseEnter` →
  `"mouseenter"`). При обновлении обработчика — всегда снять старый перед навешиванием
  нового (иначе повиснут оба).
- **`style` как объект.** Сейчас `Object.assign(dom.style, value)` при обновлении
  оставил бы «висеть» свойства, которые были в старом style-объекте, но исчезли в
  новом. `patchProps` должен диффить и style: свойства, пропавшие из `next.style`
  относительно `prev.style`, сбрасывать (`dom.style[prop] = ""`), изменившиеся/новые —
  присваивать. Отсутствие `style` в next при наличии в prev — сбросить все ранее
  заданные свойства.
- **Булевы/false-атрибуты.** Сохранить действующую конвенцию Этапа 2 (зафиксирована в
  комментарии `applyProps` и тестах `render.ts`): `value === false` → атрибут не
  ставится (а при переходе `true→false`/`present→false` — снять существующий через
  `removeAttribute`); `value === true` → `setAttribute(key, "")`; прочее →
  `setAttribute(key, String(value))`. Не-функция под `on*`-ключом → `TypeError`
  (правило Этапа 2, сохранить).

### Что меняется в `render.ts`

- Извлечь применение props из `render.ts` в общий модуль так, чтобы им пользовались и
  mount, и reconciler. Практично: определить `patchProps(dom, prevProps, nextProps)` в
  `src/reconciler.ts` (это его этап и его ответственность), а `render.ts`
  импортировать её оттуда и в `createDomNode` вызывать `patchProps(dom, {}, vnode.props)`
  (mount = патч от пустого набора props). Существующую приватную `applyProps` в
  `render.ts` удалить, чтобы не осталось двух путей применения props.
  - Допустима и обратная компоновка (общий helper в отдельном внутреннем модуле,
    импортируемый обоими) — выбор за исполнителем, критерий один: **ровно одна**
    реализация логики применения/диффа props в проекте, без дублирования правил
    `on*`/`style`/boolean.
- Регрессия обязательна: существующие тесты `src/render.test.ts` должны остаться
  зелёными без изменений (mount-поведение эквивалентно прежнему). Если пришлось
  тронуть их — это сигнал, что эквивалентность нарушена; вернуть эквивалентность, а не
  переписывать тесты.

## Алгоритм диффинга одного узла: `patchNode`

Сигнатура (имя-ориентир, менять по вкусу, но роль зафиксирована):
`patchNode(parentDom: Element, prev: VNode | null, next: VNode | null, index: number): void`
— диффит один слот ребёнка внутри `parentDom`. `index` нужен, чтобы монтировать/искать
узел на правильной позиции (`parentDom.childNodes[index]`).

Правила (из TECHNICAL_PLAN, конкретизированы):

- `prev == null && next == null` → no-op.
- `prev == null && next != null` → **mount**: создать DOM-поддерево для `next`
  (переиспользовать логику построения из `render.ts` — вынести/переиспользовать
  `createDomNode`, а не дублировать её) и вставить на позицию `index` через
  `insertBefore(newDom, parentDom.childNodes[index] ?? null)`.
- `prev != null && next == null` → **remove**: снять DOM-узел, соответствующий `prev`,
  из `parentDom` (`parentDom.childNodes[index]`), удалить (`removeChild`).
- Оба заданы, **`prev.type !== next.type`** → **replace**: построить новый DOM-узел для
  `next`, заменить старый (`replaceChild(newDom, oldDom)`). Разный тип включает случай
  «элемент ↔ текст» и «div ↔ span».
- Оба заданы, **тот же `type`**:
  - `TEXT_ELEMENT`: если `nodeValue` отличается — обновить `data`/`nodeValue`
    существующего текстового узла **на месте** (не пересоздавать), иначе no-op.
  - Обычный элемент: `patchProps(dom, prev.props, next.props)` на **существующем** DOM-узле,
    затем `patchChildren(dom, prev.props.children, next.props.children)`. DOM-узел не
    пересоздаётся — это и есть сохранение идентичности.

Реэкспортируемая `reconcile(container, prev, next)` — тонкая обёртка: делегирует в
`patchNode(container, prev, next, 0)` (корень живёт в слоте 0 контейнера). Сохранить
существующую сигнатуру `reconcile(container: Element, prev: VNode | null, next: VNode | null): void`.

## Диффинг детей: `patchChildren`

Сигнатура-ориентир: `patchChildren(parentDom: Element, prevChildren: VNode[], nextChildren: VNode[]): void`.

Дети уже нормализованы `createElement` — это всегда `VNode[]`, без примитивов/`null`.

**Смешанные списки (часть детей с `key`, часть без) — практичный выбор:**

- Если **все** дети в `nextChildren` имеют `key` (и, соответственно, работаем в keyed-режиме) —
  использовать keyed-алгоритм ниже.
- Иначе (нет ключей вовсе, либо ключи заданы лишь у части) — использовать **простое
  сопоставление по индексу**: для каждого `i` вызвать `patchNode(parentDom, prev[i] ?? null,
  next[i] ?? null, i)`; хвост (если `prev` длиннее) удалить, недостающие (если `next`
  длиннее) — смонтировать. Частично-ключевые списки намеренно НЕ пытаемся сопоставлять
  «умно» — это over-engineering для синхронного Этапа 3; ключи в таком случае просто
  не дают выгоды, но и не ломают результат.

Определять режим по признаку «у всех next-детей есть `key`» — прямолинейно и
предсказуемо. Ключ узла берётся из `vnode.props.key`.

**Keyed-алгоритм (когда у всех next-детей есть `key`):**

1. Построить `Map<key, {vnode, dom, index}>` по `prevChildren` (dom берётся из
   `parentDom.childNodes` по индексу до начала мутаций — снять снимок один раз).
2. Идти по `nextChildren` слева направо, поддерживая указатель на «куда вставлять»
   (референсный узел для `insertBefore`):
   - если для `next.key` есть запись в map → это **patch + move**: сначала
     `patchNode` над существующим DOM-узлом (те же правила одного узла), затем при
     необходимости переставить его на текущую позицию через
     `parentDom.insertBefore(dom, referenceNode)`. Пометить key как использованный.
   - если записи нет → **mount** нового узла и вставить на текущую позицию.
3. После прохода — удалить все prev-узлы, чьи key остались неиспользованными (есть в
   map, но не встретились в `nextChildren`).

Замечание для исполнителя: манипулировать реальным `childNodes` во время move-цикла
аккуратно — снимок «старых» DOM-узлов по key снять до перестановок, а `insertBefore`
корректно работает и как «переместить уже присутствующий узел». LIS не вводить.

## Функции в `src/reconciler.ts` (итоговый контур)

- `export function reconcile(container: Element, prev: VNode | null, next: VNode | null): void`
  — публичная обёртка, делегирует в `patchNode(container, prev, next, 0)`.
- `patchNode(parentDom, prev, next, index)` — дифф одного слота (mount/remove/replace/patch).
- `patchChildren(parentDom, prevChildren, nextChildren)` — индексный либо keyed-режим.
- `patchProps(dom, prevProps, nextProps)` — единая функция применения/диффа props
  (add/update/remove для атрибутов, `on*`-обработчиков через remove/add, `style` с
  диффом свойств). Экспортировать её или сделать доступной `render.ts` (см. выше).
- Переиспользовать построение DOM-поддерева при mount/replace: вынести/переиспользовать
  `createDomNode` из `render.ts` вместо дублирования (например, экспортировать её как
  internal и импортировать в reconciler, либо перенести в общий модуль). Не заводить
  вторую копию логики создания узла.

Имена внутренних функций — на усмотрение исполнителя; зафиксированы их роли и
сигнатура публичного `reconcile`.

## Тест-кейсы `src/reconciler.test.ts`

Стиль — как в проекте: jsdom-контейнер, утверждения на **итоговом DOM-дереве**
(`root.innerHTML`, обход `childNodes`, атрибуты, сработавшие обработчики). Расширяет
список из TECHNICAL_PLAN, не заменяет его.

Из TECHNICAL_PLAN (базовый минимум):
1. Смена текста узла (`h("p", null, "a")` → `"b"`): текст обновился.
2. Добавление атрибута (не было `id` → появился `id`).
3. Удаление атрибута (был `id` → нет `id`; `getAttribute` вернул `null`).
4. Добавление обработчика (не было `onClick` → появился; клик срабатывает).
5. Удаление обработчика (был `onClick` → нет; после diff клик НЕ вызывает старый
   обработчик — счётчик вызовов не растёт).
6. Добавление ребёнка в конец списка.
7. Удаление ребёнка из списка.
8. Переупорядочивание детей.
9. Замена узла при смене типа (`div` → `span`; `element` ↔ `TEXT_ELEMENT`).
10. **Сохранение DOM-идентичности**: взять ссылку на DOM-узел до `reconcile`, после
    патча props/детей — тот же самый объект (`expect(after).toBe(before)` / `===`).

Дополнительно (расширение):
11. **Обновление значения обработчика**: `onClick` заменён на другую функцию — старый
    больше не вызывается, новый вызывается (проверяет корректный `removeEventListener`
    по ссылке из `prev.props`).
12. **Обновление атрибута** (изменилось значение существующего `id`/`class`).
13. **`style`-дифф**: свойство, исчезнувшее из нового `style`, сброшено на элементе;
    изменившееся — обновлено; неизменные не трогаются.
14. **Булевы атрибуты**: `disabled: true` → `disabled: false` снимает атрибут;
    обратный переход ставит.
15. **`prev == null` → mount** через `reconcile` (первый рендер поведёт себя как
    `render`) и **`next == null` → полное удаление** корня из контейнера.
16. **Keyed reconcile**: список с `key` переставлен (`[a,b,c]` → `[c,a,b]`) — DOM-узлы
    соответствующих ключей **сохранили идентичность** (не пересозданы), порядок в
    контейнере корректный.
17. **Keyed insert/remove в середину**: `[a,b,c]` → `[a,x,b,c]` (вставка) и
    `[a,b,c]` → `[a,c]` (удаление среднего) — уцелевшие узлы сохраняют идентичность.
18. **Рекурсивный патч вложенности**: изменение в глубоко вложенном ребёнке не
    пересоздаёт неизменных предков/сиблингов (идентичность внешних узлов сохранена).
19. **Индексный режим без ключей**: `[a,b]` → `[a,b,c]` и `[a,b,c]` → `[a,b]`
    (add/remove хвоста) корректны и не пересоздают неизменные узлы по индексу.
20. **Смешанный список** (часть с `key`, часть без) — по выбранному правилу падает в
    индексный режим и даёт корректный итоговый DOM (тест фиксирует принятое поведение,
    а не «умное» keyed-сопоставление).
