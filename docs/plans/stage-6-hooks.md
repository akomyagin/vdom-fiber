# План Этапа 6 — Hooks (`useState`) + функциональные компоненты

Файлы-исполнители: `src/hooks.ts` (+ `src/hooks.test.ts`), `src/fiber.ts`,
`src/types.ts`, `src/scheduler.ts`, `src/index.ts`.
Первоисточник требований: `docs/TECHNICAL_PLAN.md`, раздел «Этап 6 — Hooks
(`useState`)». Этот план его уточняет и расширяет, но НЕ отменяет: пер-fiber список
хуков с сопоставлением по порядку вызова (rules of hooks); `useState(initial)` →
`[state, setState]`, где `setState` кладёт обновление в очередь хука и планирует
re-render владельца через scheduler Этапа 5; поддержка функциональных компонентов
как `type` VNode (функция → вызов, дети из результата); демо-счётчик, обновляющийся
по клику через собственный конвейер; DoD — счётчик работает end-to-end через
собственный VDOM + Fiber + scheduler + hooks.

Этап 6 — последний по MVP-плану. Его главная техническая трудность не в самом
`useState` (по сути это индекс в массиве + замыкание), а в том, что он впервые
требует **функциональных компонентов**: все предыдущие этапы явно предполагали, что
`type` — это строка (DOM-тег или `TEXT_ELEMENT`). Хук без функционального компонента
некуда «прикрепить». Поэтому центр тяжести плана — корректно вплести функциональные
компоненты в нерекурсивный Fiber-обход (Этап 4) и в commit, не сломав инварианты
Этапов 4-5.

## Цель

1. Расширить модель VNode/Fiber так, чтобы `type` мог быть функцией-компонентом
   `(props) => VNode | null`, не теряя типобезопасность host-ветки и `TEXT_ELEMENT`.
2. Научить Fiber-обход вызывать функцию-компонент в своей единице работы: вызвать её
   с `props`, получить дочернее VNode-дерево и продолжить обход по нему — при этом сам
   fiber компонента **не имеет собственного DOM-узла** (он «прозрачен» для DOM).
3. Научить commit проходить сквозь такие dom-less компонентные fiber'ы: находить
   ближайший host-родитель для размещения детей и не пытаться создавать/патчить DOM
   для самого компонента (в т.ч. для DELETION компонентного поддерева).
4. Реализовать `useState`: пер-fiber список хуков, сопоставление по порядку вызова,
   переживание состояния между рендерами через `alternate`, `setState` → очередь
   обновлений хука + планирование re-render владельца через `scheduleWork`.
5. Свести всё в рабочий end-to-end счётчик и покрыть тестами на итоговом DOM.

## Границы (что НЕ входит в Этап 6)

Явно вне объёма — не трогать:

- **Прочие хуки** (`useEffect`, `useMemo`, `useRef`, `useReducer`, `useContext`) —
  не в объёме MVP. Реализуется только `useState`. Инфраструктуру (пер-fiber список
  хуков, указатель «текущий fiber») спроектировать так, чтобы она не мешала добавить
  их позже, но самих хуков не писать.
- **JSX** — по-прежнему запрещён в MVP (SKILL.md). Компоненты пишутся как обычные
  функции, возвращающие результат `h(...)`. Демо-счётчик — на hyperscript-API.
- **Батчинг нескольких `setState` в одном тике/событии** в React-стиле
  (`unstable_batchedUpdates`) — не обязателен. Достаточно, чтобы каждый `setState`
  запланировал re-render; несколько подряд могут дать несколько рендеров или один —
  главное, чтобы итоговый DOM был корректен. Не усложнять ради батчинга.
- **Мемоизация / `React.memo` / bailout по неизменившимся props** — не в объёме.
  Функциональный компонент вызывается на каждом рендере своего поддерева.
- **Error boundaries, Suspense, ключи-как-reset-состояния, контекст** — вне объёма.
- **Изменение модели приоритетов и логики вытеснения в `scheduler.ts`** — не трогать.
  Правки в scheduler.ts ограничены тем, что нужно, чтобы `setState` мог найти
  контейнер и верхнеуровневый VNode для повторного `scheduleWork` (см. развилку 5).
  Логику `workLoop`/`shouldYield`/`startNextPendingRender`/вытеснения не менять.
- **`reconcile`/`render` Этапов 2-3** — синхронный путь остаётся как есть. Он НЕ
  обязан поддерживать функциональные компоненты (это отдельный, не Fiber-путь).
  Функциональные компоненты живут в Fiber-конвейере (`scheduleWork`). Если хочется —
  можно оставить в `reconcile` явный отказ/необработку функционального `type`, но не
  тратить силы на дублирование поддержки компонентов во втором пути.

## Что уже есть и переиспользуется (не дублировать)

- `createElement(type, props, ...children)` — фабрика VNode. Сейчас параметр `type:
  string`. Расширить сигнатуру, чтобы принимала и функцию-компонент (см. развилку 1),
  сохранив нормализацию детей как есть.
- `createWorkInProgress`, `performUnitOfWork`, `commitRoot` в `fiber.ts` — обход и
  commit. Точки врезки функциональных компонентов — внутри них (развилки 2, 3).
- `isKeyedChildren`, `matchIndexedChildren`, `matchKeyedChildren` в `fiber.ts` —
  сопоставление детей по `===` на `type`. Для функций `===` работает по ссылке
  автоматически, если типы расширены; логику матчинга менять НЕ требуется.
- `createDomNode`, `patchProps` (`reconciler.ts`) — создание/патч host-узлов. Их не
  менять: они вызываются только для host-fiber'ов, компонентные fiber'ы до них не
  доходят.
- `scheduleWork(container, nextVNode, priority)` (`scheduler.ts`) — единственная точка
  входа в конвейер. `setState` вызывает именно её (развилка 5).

## Пять развилок — обязательные явные решения

Это ядро плана: то, что холодная модель-исполнитель не выведет дёшево сама. Каждая
развилка ниже — принятое решение с обоснованием и рамками. Отклоняться от них можно
только если по ходу вскроется прямая невозможность — тогда зафиксировать почему.

### Развилка 1 — Типы (`src/types.ts`, `src/fiber.ts`)

**Решение.** Ввести тип функции-компонента и расширить `VNode.type` и `Fiber.type`
до объединения «строка | функция-компонент», сохранив типобезопасность
`TEXT_ELEMENT`-ветки и host-ветки.

- В `types.ts` добавить экспортируемый тип, например:
  `export type ComponentFunction = (props: VProps) => VNode | null;`
  Компонент получает свой `props`-бэг (тот же `VProps` с `children`) и возвращает одно
  VNode-поддерево или `null` (компонент, ничего не рендерящий). Возврат одного VNode
  (не массива) — сознательное упрощение: фрагменты вне объёма MVP.
- `VNode.type: string | ComponentFunction`. `Fiber.type?: string | ComponentFunction`.
- **Не терять различение host/text/component.** Downstream-код различает ветки по
  `typeof fiber.type === "function"` (компонент) и `fiber.type === TEXT_ELEMENT`
  (текст); всё остальное строковое — host-тег. Ввести маленький предикат-хелпер
  (напр. `isComponentFiber` / `isFunctionType`), чтобы проверка была в одном месте, а
  не размазана `typeof ... === "function"` по коду.
- **Типобезопасность host-ветки.** Там, где `createDomNode`/`patchProps` требуют
  строковый тег (`document.createElement(type)`), тип уже сужен тем, что компонентные
  fiber'ы туда не попадают (развилка 3). Сохранить это инвариантом: `createDomNode`
  по-прежнему принимает VNode со строковым `type`; в местах вызова гарантировать
  сужение (компонент отсеян ветвлением выше), а не ослаблять сигнатуру `createDomNode`.
- `createElement` в `createElement.ts`: расширить параметр `type` до
  `string | ComponentFunction`; тело не меняется (нормализация детей та же). `h`-алиас
  тот же.

**Рамки.** Не вводить классовые компоненты, не вводить отдельный «тег фрагмента».
Объединение ровно `string | ComponentFunction`.

### Развилка 2 — Где вызывается функция-компонент в обходе (`src/fiber.ts`)

**Решение.** Вызов компонента происходит **внутри `performUnitOfWork` / его
child-reconciliation для данного fiber'а**, когда обрабатывается fiber, чей `type` —
функция. Это НЕ рекурсия по фиберам и НЕ нарушает нерекурсивность обхода: это обычный
синхронный вызов JS-функции внутри одной единицы работы, дающий VNode, который
становится **единственным ребёнком** этого компонентного fiber'а.

Механика (на уровне «чего добиться», конкретную форму выбирает исполнитель):

- Когда `performUnitOfWork` обрабатывает fiber с `typeof type === "function"`:
  - подготовить хук-контекст этого fiber'а (развилка 4): выставить «текущий
    рендерящийся fiber», обнулить индекс хука, перенести список хуков с `alternate`
    (переживание состояния);
  - вызвать `type(fiber.props)` → получить один VNode (или `null`);
  - трактовать результат как список детей `[vnode]` (или `[]`, если `null`) и прогнать
    штатный `reconcileChildren` — то есть у компонентного fiber'а ровно один
    «следующий ребёнок» = возвращённое поддерево. Матчинг с prev-детьми
    (`alternate.props.children`) должен для компонентного fiber'а браться из его
    **прошлого отрендеренного результата**, а не из `props.children` — см. ниже.
- Для **host-fiber'ов** поведение прежнее: `reconcileChildren` по `props.children`.

**Важная тонкость про prev-детей компонентного fiber'а.** Существующий
`reconcileChildren` берёт `nextChildren = fiber.props.children` и
`prevChildren = fiber.alternate?.props.children`. Для компонента «дети» — это не
`props.children`, а результат вызова функции. Значит для компонентной ветки нужно
подать в сопоставление next = `[renderResult]`, prev = отрендеренный результат прошлого
раза. Прошлый результат доступен как дети `alternate` компонентного fiber'а (т.е. то,
что в прошлый commit висело на `alternate.child`), а его backing-DOM — через host-детей
ниже. Решение: развести две ветки в `reconcileChildren` (или в вызывающем коде) —
host-ветка сопоставляет `props.children`, компонентная ветка сопоставляет
`[renderResult]` против прошлого результата, но **обе используют один и тот же матчинг
пар** (`matchIndexedChildren`/`matchKeyedChildren`) и одну и ту же логику spawn'а
child-fiber'ов. Не дублировать матчинг — вынести общее.

**Нерекурсивность (инвариант Этапа 4) сохраняется:** `performUnitOfWork` по-прежнему
возвращает «следующий fiber» (child → sibling → подъём) и не вызывает себя рекурсивно.
Вызов `type(props)` — единичный синхронный вызов внутри шага, он лишь порождает
`fiber.child`. Прерывание между единицами работы остаётся безопасным: вызов функции-
компонента происходит в render-фазе и DOM не трогает (компонент — чистая функция от
props/state относительно DOM; побочный эффект только на хук-состоянии этого fiber'а).

**Prev-side DOM для детей компонента.** `reconcileChildren` вычисляет
`prevParentDom = fiber.alternate?.dom` и берёт `childNodes.item(i)`. У компонентного
fiber'а `dom === null`. Значит для компонентной ветки prev-DOM детей нельзя брать из
`alternate.dom`. Нужно, чтобы backing-DOM переживших UPDATE-детей брался из
соответствующих fiber'ов прошлого результата (у которых dom уже проставлен), а не из
`childNodes` несуществующего родителя. Практически: для компонентной ветки строить
`prevSlots` не по `parentDom.childNodes[i]`, а по `dom` прошлого child-fiber'а
компонента. Это ключевая правка — без неё UPDATE детей компонента потеряет DOM-identity
и всё будет пересоздаваться (или падать на `null`). Исполнитель должен решить это явно,
переживая прошлый child-fiber компонента через `alternate`.

### Развилка 3 — Host-fiber lookup в commit (`src/fiber.ts`)

**Решение.** Commit должен трактовать компонентные fiber'ы как **прозрачные** (dom-less
pass-through): они не создают свой DOM-узел, а их дети размещаются в ближайшем
host-предке; их поддерево при DELETION удаляется через ближайшие host-потомки.

Сейчас есть три завязки на «у fiber есть dom»:

1. **`commitFiber` PLACEMENT** вызывает `createDomNode({type, props})` — для функции
   это упадёт (`document.createElement(function)`). Компонентный fiber в PLACEMENT НЕ
   создаёт узел: он должен вернуть/разместить DOM своего поддерева. Поскольку commit
   для host-PLACEMENT строит весь subtree одним `createDomNode` и НЕ спускается в
   child-fiber'ы, а компонент между хостами — нужен механизм «спуститься сквозь
   компонент к его host-детям и разместить их». Решение: для компонентного fiber'а
   commit **спускается в его child-fiber'ы** (в отличие от host-PLACEMENT, где спуск
   запрещён), находит там host-fiber'ы (или снова компоненты — рекурсивно вниз) и
   размещает их DOM в host-родителе. То есть: если корень поддерева, которое надо
   разместить, — компонент, PLACEMENT «разворачивается» до множества host-узлов
   нижнего уровня.
2. **`commitChildren` читает `parentFiber.dom`** и выходит в `null`-ветку, если dom
   нет. Для компонентного родителя `dom === null` — но детей всё равно надо разместить
   в **ближайшем host-предке**. Решение: ввести «поиск ближайшего host-родителя вверх
   по `parent`» (подниматься по `.parent`, пропуская компонентные fiber'ы, пока не
   встретится fiber с `dom !== null`; на корне это контейнер). Использовать найденный
   host-DOM как `parentDom` для размещения. Аналогично «ближайший host-сосед» для
   вычисления `refNode`/`lastPlaced`: позиционирование должно считаться в координатах
   host-родителя, а компонентные уровни между ними — пропускаться.
3. **DELETION (`addDeletion` кладёт запись на `parent`).** Если удаляемый prev-ребёнок
   сам компонент — у него `dom === null`, и `commitChildren`-ветка удаления
   (`parentDom.removeChild(deletion.dom)`) не сработает. Решение: удаление компонента —
   это удаление всех его host-узлов нижнего уровня. При DELETION компонентного fiber'а
   найти его host-потомки (спуск вниз сквозь компонентные уровни до первых host-узлов)
   и удалить их из host-родителя. Причём host-родитель удаления — это ближайший
   host-предок точки, где висел компонент (та же логика «вверх до dom»). Если у самого
   удаляемого prev-компонента сохранён его прошлый child-результат (через прошлый
   commit), спуск идёт по нему.

**Итоговый инвариант commit:** «родитель для размещения/удаления host-узла — это
ближайший fiber вверх с `dom !== null`; поддерево host-узлов компонента — это ближайшие
host-узлы вниз сквозь компонентные уровни». Реализовать два хелпера:
`getHostParentDom(fiber)` (вверх) и «собрать host-узлы поддерева» (вниз), и провести
через них PLACEMENT, позиционирование и DELETION. Это самая объёмная правка Этапа 6 —
её нельзя срезать: без неё компонент как корень или компонент среди host-детей не
коммитится.

**Рамки.** Не переписывать `commitRoot`/`commitChildren` целиком «с нуля» без нужды —
достроить их так, чтобы host-fiber'ы обрабатывались как раньше (регрессий Этапа 4/5
быть не должно), а компонентные — по новым правилам прозрачности. Все существующие
тесты `fiber.test.ts`/`scheduler.test.ts` должны остаться зелёными.

### Развилка 4 — Хранение списка хуков и «текущего рендерящегося fiber»

**Решение по хранению списка хуков.** Список хуков живёт **на самом `Fiber`** (новое
опциональное поле, напр. `hooks?: Hook[]`), где `Hook` для `useState` хранит текущее
`state` и очередь ожидающих обновлений (`queue: Array<S | ((prev:S)=>S)>`). Это
согласуется с тем, как `props`/`dom` уже переживают между рендерами через `alternate`:
при подготовке компонентного fiber'а к рендеру список хуков переносится с
`fiber.alternate.hooks` (прошлый отрендеренный fiber компонента). Порядок вызова
`useState` в теле компонента даёт индекс в этом массиве — отсюда rules of hooks
(нельзя вызывать хуки условно, иначе индексы разъедутся; в объёме MVP это не
проверяется рантаймом, только документируется).

- Добавить в `Fiber` поле `hooks?: Hook[]` (тип `Hook` определить в `hooks.ts` и
  импортировать, либо объявить структурный тип в `fiber.ts` — выбрать так, чтобы не
  создать циклический импорт; предпочтительно определить тип хука в `hooks.ts`, а в
  `fiber.ts` держать поле как generic/`unknown[]` или импортировать тип-только).
- При рендере компонентного fiber'а: `wipFiber.hooks = []`, индекс хука `= 0`; каждый
  `useState` читает `alternate.hooks[index]` (если есть) для переноса `state` и
  применения накопленной `queue`, затем кладёт свежий Hook в `wipFiber.hooks[index]`.

**Решение по указателю «текущий рендерящийся fiber» — где живёт module-state.**
Указатель на «фибер, который сейчас рендерится» и «индекс текущего хука» живут как
**module-state в `hooks.ts`** (новый маленький владелец состояния, по образцу того,
как `scheduler.ts` — единственный владелец `current`-дерева).

Обоснование выбора (это то, что план обязан обосновать):

- **Не в `fiber.ts`.** По конвенции Этапа 4 `fiber.ts` намеренно stateless (см. его
  докблок: «No module-level state»). Класть туда указатель «текущий fiber» нарушило бы
  этот инвариант ради хуков. Не делать.
- **Не в `scheduler.ts`.** Scheduler владеет `current`-деревом и очередью — это его
  зона. Указатель «текущий рендерящийся компонент» — это состояние **вызова функции-
  компонента**, а не планирования; смешивать его с приоритетами/WIP значило бы
  размазать ответственность и усложнить и без того нагруженный module-state
  планировщика.
- **Не явным параметром.** Прокидывать «текущий fiber» параметром до `useState`
  невозможно: `useState` вызывается из **тела пользовательского компонента**, между
  ним и обходом — вызов произвольной пользовательской функции, которая про fiber
  ничего не знает и не может пробросить параметр. Именно поэтому React использует
  «dispatcher»/текущий-fiber через модульное состояние. Это архитектурно вынужденный
  module-state, а не удобство.
- **Итог:** `hooks.ts` экспортирует внутренние функции (напр. `beginHooks(fiber)` /
  `finishHooks()` или `setCurrentFiber(fiber)`), которые `fiber.ts` вызывает вокруг
  `type(props)`, устанавливая/сбрасывая module-local `currentFiber` и `hookIndex`.
  `useState` читает этот `currentFiber`. Так `fiber.ts` остаётся без **своего**
  состояния (он лишь дёргает API hooks.ts), а новое состояние сосредоточено в hooks.ts.
  Учесть возможный цикл импортов `fiber.ts ↔ hooks.ts`: разрулить через `import type`
  и/или узкий рантайм-API, чтобы граф импортов оставался ацикличным на уровне значений.

**Рамки.** Не строить общий «dispatcher»-механизм на несколько хуков — достаточно
`useState`. Не хранить указатель в глобальном `window`/`globalThis`.

### Развилка 5 — `setState` → `scheduleWork`

**Решение.** `setState` из замыкания хука должен: (1) записать обновление в очередь
своего Hook (на своём fiber'е); (2) найти **контейнер** и **верхнеуровневый VNode**,
которые нужно повторно подать в `scheduleWork`, и вызвать его для перерендера всего
дерева этого контейнера.

Развилка в том, что `scheduleWork(container, nextVNode, priority)` принимает **полное**
следующее VNode-дерево и контейнер, а `setState` знает только про свой fiber. Решения
по обоим недостающим аргументам:

- **Как найти `container`.** Подняться от fiber'а по `.parent` до корня; корневой
  host-fiber несёт `dom = container` (см. `createWorkInProgress`: у корня
  `dom = container`). То есть `container = <ближайший корневой fiber>.dom as Element`.
  Реализовать подъём как хелпер (может переиспользовать «вверх до корня» из commit-
  логики). Замыкание `setState` должно захватить ссылку на **свой fiber** (тот, что
  был «текущим» в момент вызова `useState`) — этого достаточно, чтобы дойти до корня.
  Тонкость: между рендерами fiber пересоздаётся (WIP↔alternate), поэтому `setState`
  должен адресовать **актуальный** источник истины состояния. Практика React: очередь
  обновлений хранится на объекте, переживающем рендеры. Здесь очередь живёт на Hook, а
  Hook переносится через `alternate`. Решение: `setState` пишет в очередь Hook (объект
  Hook можно переиспользовать/переносить между рендерами так, чтобы `setState`,
  захваченный в первом рендере, дописывал в ту же логическую ячейку) — либо, проще для
  учебного объёма, `setState` кладёт обновление и планирует перерендер, а применение
  очереди происходит при следующем рендере по индексу хука. Исполнителю: обеспечить,
  чтобы `setState` из старого рендера доносил обновление до состояния, читаемого новым
  рендером (перенос очереди через alternate по индексу — минимально достаточный
  механизм). Это единственное место, где нужна аккуратность с identity — покрыть тестом
  «setState из обработчика, навешенного в первом рендере, работает после нескольких
  обновлений».
- **Какой VNode передать в `scheduleWork`.** Тот же **верхнеуровневый VNode**, который
  приложение изначально подало в контейнер (корень дерева), — не поддерево компонента.
  Перерендер идёт от корня: scheduler возьмёт prev из своего `current`-дерева этого
  контейнера и продиффит. Значит нужно, чтобы этот верхнеуровневый VNode был где-то
  сохранён и доступен `setState`. **Он уже сохранён** — в `scheduler.ts` как
  `currentVNode` для `currentContainer`. Решение: экспортировать из `scheduler.ts`
  узкую функцию «перепланировать текущее дерево контейнера», напр.
  `scheduleRerender(container, priority?)`, которая внутри берёт сохранённый
  `currentVNode` для этого контейнера и зовёт `scheduleWork(container, currentVNode,
  priority)`. `setState` вызывает `scheduleRerender(container)`. Так `setState` не
  обязан сам знать/хранить верхнеуровневый VNode — источник истины остаётся один
  (`currentVNode` в scheduler.ts), а hooks.ts не дублирует хранение дерева.
  - Приоритет по умолчанию для re-render от `setState` — `Priority.Normal` (или
    `UserBlocking`, если обосновать, что клики — user-blocking; выбрать один и
    зафиксировать в коде комментарием; для учебного счётчика достаточно `Normal`).
  - Это единственная разрешённая правка `scheduler.ts` по существу: добавить
    `scheduleRerender`, не меняя `workLoop`/вытеснение/очередь.

**Рамки.** Не заводить в hooks.ts собственную копию «верхнеуровневого VNode на
контейнер» — переиспользовать `currentVNode` планировщика через новую узкую функцию.
Не трогать модель приоритетов.

## Совместимость с инвариантами Этапов 4/5 (не сломать)

- **Нерекурсивность render-обхода.** `performUnitOfWork` остаётся не-рекурсивной по
  фиберам; вызов `type(props)` — синхронный вызов JS-функции внутри одной единицы
  работы, порождающий `fiber.child`. Прерывание между единицами работы по-прежнему
  безопасно (render-фаза не трогает DOM; вызов компонента чист относительно DOM).
- **Keyed/indexed matching.** Сравнение `type` через `===` уже корректно для функций
  по ссылке после расширения типов; матчинг детей не переписывать.
- **Приоритеты и вытеснение в `scheduler.ts`.** Не менять. Единственная добавка —
  `scheduleRerender` (тонкая обёртка над `scheduleWork` с сохранённым `currentVNode`).
- **Атомарность commit.** commit остаётся синхронным и неделимым; добавляется только
  прозрачный проход сквозь компонентные fiber'ы (host-parent вверх, host-узлы вниз).
- **`fiber.ts` без собственного module-state.** Новое состояние (текущий fiber, индекс
  хука) живёт в `hooks.ts`; `fiber.ts` лишь вызывает его API вокруг рендера компонента.
- **Существующие тесты** `fiber.test.ts`, `scheduler.test.ts`, `reconciler.test.ts`,
  `render.test.ts` — должны остаться зелёными без правок их ожиданий (host-путь не
  меняет поведение). Если какой-то тест приходится править — это сигнал регрессии,
  разобраться, а не подгонять ожидание.

## Тест-кейсы (jsdom + Vitest, проверка на итоговом DOM)

Из TECHNICAL_PLAN (обязательные):

1. **Начальный рендер функционального компонента.** `scheduleWork(container,
   h(Counter, null), ...)` где `Counter` использует `useState` — DOM отражает начальное
   состояние. Проверить `container.innerHTML`.
2. **`setState` обновляет DOM.** Компонент-счётчик; после `setState`/клика по кнопке —
   DOM показывает новое значение (прогнать конвейер до commit; в тестах — синхронно,
   т.к. короткий рендер коммитится внутри `scheduleWork`; учесть инъекцию
   scheduler-deps как в `scheduler.test.ts`, если рендер длинный).
3. **Несколько независимых состояний в одном компоненте.** Два `useState` в одном
   компоненте; обновление одного не затирает другой; индексы хуков не путаются.
4. **Функциональный апдейтер `setState(prev => next)`.** `setState(c => c + 1)`
   вызванный дважды подряд даёт `+2` (или корректно применяет функциональную форму) —
   проверить, что апдейтер получает актуальный prev, а не устаревший захват.

Дополнительные (закрывают дизайн-гэп — обязательны к покрытию):

5. **Функциональный компонент как корень дерева.** `h(App, null)` подан прямо в
   контейнер — commit размещает host-узлы результата прямо в контейнере (host-parent =
   контейнер, компонент прозрачен).
6. **Компонент, рендерящий другой компонент (вложенность).** `Outer` возвращает
   `h(Inner, ...)`; хуки обоих не пересекаются; DOM корректен. Проверяет цепочку
   dom-less уровней вверх/вниз в commit.
7. **Компонент среди host-детей в списке.** `h("div", null, h("span", null, "a"),
   h(Widget, null), h("span", null, "b"))` — Widget вставлен между host-детьми;
   позиционирование (`refNode`/`lastPlaced`) корректно считается в координатах
   host-родителя (`div`), Widget не занимает «слот» с собственным DOM, но его host-узлы
   встают на правильное место между `span`-ами.
8. **Обновление внутри компонента сохраняет DOM-identity неизменённых узлов.** После
   `setState`, меняющего один текстовый узел, соседние host-узлы поддерева компонента
   НЕ пересоздаются (сравнить идентичность `Node` до/после) — проверяет корректный
   перенос prev-DOM детей компонента через `alternate` (развилка 2, тонкость).
9. **Удаление компонента из дерева (DELETION компонентного поддерева).** Переход от
   дерева с компонентом к дереву без него (или `cond && h(Comp)` → `false`) удаляет
   все host-узлы компонента из host-родителя (развилка 3, DELETION).
10. **`setState` из обработчика первого рендера работает после нескольких обновлений.**
    Обработчик `onClick`, навешенный в первом рендере, при многократном клике
    доносит обновления до актуального состояния (развилка 5, identity очереди хука).
11. **Демо-счётчик end-to-end** (DoD): кнопка + текст; клик увеличивает счётчик; DOM
    обновляется через собственный VDOM + Fiber + scheduler + hooks. Симулировать клик
    (`button.dispatchEvent(new Event("click"))` или `.click()`), утвердить на DOM.

Где рендер может не уместиться в один бюджет — использовать инъекцию scheduler-deps
(`__setSchedulerDeps`) и «прокрутку» тиков, как в `scheduler.test.ts`; для коротких
компонентов достаточно синхронного пути (`scheduleWork` коммитит до возврата).
