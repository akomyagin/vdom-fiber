# План Этапа 5 — Планировщик (прерываемый work loop + приоритеты + вытеснение)

Файл-исполнитель: `src/scheduler.ts` (+ `src/scheduler.test.ts`).
Первоисточник требований: `docs/TECHNICAL_PLAN.md`, раздел «Этап 5». Этот план его
уточняет и расширяет, но НЕ отменяет: work loop, вызывающий `performUnitOfWork` в
цикле до исчерпания бюджета кадра (`shouldYield()` по дедлайну), уступка потока через
`MessageChannel`-тик (фолбэк `setTimeout(0)`/`requestIdleCallback`), очередь приоритетов
`Immediate/UserBlocking/Normal/Idle`, вытеснение идущего низкоприоритетного рендера
более приоритетным обновлением, разнесение фаз `render` (прерываемая) / `commit`
(синхронная, неделимая), и DoD — длинный рендер не блокирует поток одним синхронным
проходом, приоритеты соблюдаются, результат идентичен синхронной версии — всё входит
в объём как есть.

## Цель

Подключить Fiber-обход Этапа 4 к прерываемому планировщику. Этап 5 — первый, где
`performUnitOfWork` реально вызывается в цикле. Планировщик:

1. владеет очередью ожидающих обновлений с приоритетами;
2. гоняет render-фазу time-sliced чанками: `while (nextUnitOfWork && !shouldYield())`,
   уступая поток браузеру по исчерпании бюджета кадра и возобновляясь с сохранённого
   указателя;
3. по завершении render-фазы (`nextUnitOfWork === null`) вызывает синхронный неделимый
   `commitRoot` и делает свежее WIP-дерево новым `current`;
4. при поступлении более приоритетного обновления во время идущего рендера — **вытесняет**
   текущий WIP: выбрасывает недостроенное дерево и начинает render заново с более
   приоритетным корнем.

Ключевое архитектурное решение этапа, которое Этап 4 сознательно отложил: **где живёт
`current`-дерево (последнее закоммиченное) между вызовами `scheduleWork`.** Ответ:
module-level state в `scheduler.ts` (см. ниже). `fiber.ts` по-прежнему без persistent-state.

## Границы (что НЕ входит в Этап 5)

Явно вне объёма — не трогать:

- **Hooks / `useState` / функциональные компоненты** — Этап 6. `scheduler.ts` работает с
  host-VNode-деревьями (`div`/`TEXT_ELEMENT`), как и Этап 4. `setState`, который будет
  дёргать `scheduleWork` для re-render владельца, — это Этап 6, здесь его нет.
- **Полная React-подобная lane-модель** приоритетов (битовые lanes, батчинг по lane,
  entanglement, expiration-времена) — избыточна для учебного объёма. Достаточно
  плоского `enum Priority` из 4 уровней и сравнения чисел. Не вводить lanes.
- **Реальные измерения кадра / requestAnimationFrame-луп** — не нужны. Бюджет кадра —
  простая константа (по умолчанию ~5 мс), дедлайн вычисляется от инъектируемого `now()`.
- **`commitRoot` не переписывается** — она полностью реализована в Этапе 4 и корректна.
  Этап 5 только решает КОГДА её звать и гарантирует, что commit синхронен и неделим
  (не прерывается `shouldYield`, в отличие от render-фазы).
- **`reconcile`/`render` Этапов 2-3 остаются как есть** — их не удалять и не менять.
  Они остаются рабочим синхронным путём; Fiber-конвейер через `scheduleWork` — второй,
  прерываемый путь. (Связывать их в один публичный API — не задача Этапа 5.)
- **Отмена уже возобновлённого тика при вытеснении не обязана быть «настоящей»**
  (нет нужды в `port.close()` или очистке очереди MessageChannel): достаточно того, что
  тик-callback перечитывает module-state и сам обнаруживает, что WIP-корень сменился
  (см. «Вытеснение», защита от stale-тика).

## Что уже есть и переиспользуется (не дублировать)

- `createWorkInProgress(container, prevVNode, nextVNode): Fiber` — готовит корневой
  host-fiber для одного рендера, моделируя prev/next явно. Именно сюда подаётся prev-дерево
  из `current`-состояния планировщика.
- `performUnitOfWork(fiber): Fiber | null` — один шаг DFS, не трогает DOM, возвращает
  следующий unit (или `null` в конце). Указатель хранит вызывающая сторона — теперь это
  scheduler.
- `commitRoot(rootFiber): void` — синхронный неделимый commit накопленных эффектов.
- Тип `Fiber` из `fiber.ts`.
- `enum Priority { Immediate=0, UserBlocking=1, Normal=2, Idle=3 }` — уже в `scheduler.ts`,
  оставить как есть (меньше число = приоритетнее). Экспорт из `index.ts` уже настроен.

## Архитектурные решения (обязательно закрыть все)

### 1. Публичная сигнатура `scheduleWork` — сменить относительно заглушки

Текущая заглушка `scheduleWork(root: Fiber, priority: Priority)` архитектурно неудобна:
внешний код не должен строить `Fiber` сам, а при повторных вызовах планировщик обязан
знать prev-дерево — а его в готовом `Fiber` нет. Поэтому **финальная публичная сигнатура:**

```ts
export function scheduleWork(
  container: Element,
  nextVNode: VNode | null,
  priority: Priority = Priority.Normal,
): void
```

Обоснование:
- планировщик сам держит `currentRoot` (последнее закоммиченное дерево для этого
  `container`) и сам зовёт `createWorkInProgress(container, prevVNode, nextVNode)` —
  внешнему коду не нужно ничего знать про `Fiber`;
- повторный вызов на том же `container` теперь корректен: prev берётся из `currentRoot`;
- `nextVNode === null` — легальный «размонтировать корень» (согласуется с
  `createWorkInProgress(..., null)` и `reconcile(..., null)`);
- дефолт `Priority.Normal` — самый частый кейс фонового обновления.

`index.ts` уже ре-экспортирует `scheduleWork`/`Priority` — правки экспорта не требуются,
если не появится новых публичных символов. Инъекция тестовых зависимостей (см. §3) —
через **отдельную** необязательную точку, чтобы не засорять основную сигнатуру.

### 2. Где живёт `current`-дерево — module-level state в `scheduler.ts`

`fiber.ts` не хранит `current` осознанно (см. handoff Этапа 4). Планировщик заводит
module-level состояние. Форма — на усмотрение исполнителя, но требования:

- нужно хранить **последнее закоммиченное WIP-дерево** (его корневой `Fiber`), чтобы
  следующий `scheduleWork` знал prev. Достаточно `let currentRoot: Fiber | null = null`.
- нужно помнить **VNode**, из которого построено текущее `current`, чтобы подать его как
  `prevVNode` в `createWorkInProgress` следующего рендера. Практичнее хранить именно
  prev-VNode отдельно (`let currentVNode: VNode | null = null`), а не пытаться извлечь
  его из `currentRoot` — так проще и надёжнее. Держать оба в паре, обновлять их атомарно
  сразу после успешного `commitRoot`.
- **привязка к контейнеру.** Для учебного объёма достаточно поддержать один активный
  `container` за раз (как и `render`/`reconcile`, которые пишут в slot 0). Тогда
  `currentRoot`/`currentVNode` — простые module-переменные, плюс `let currentContainer:
  Element | null`. Если `scheduleWork` вызывают с другим `container`, чем текущий
  незакоммиченный, — это смена цели: сбросить состояние под новый контейнер. Полноценный
  per-container `WeakMap<Element, {root, vnode}>` — допустимое, но НЕ обязательное
  усложнение; выбрать простой вариант, если тесты не требуют мультиконтейнерности
  (см. тест-кейсы — они одно-контейнерные).

Инвариант: `currentVNode` — это то, что реально сейчас в DOM. Обновлять его строго
**после** commit, никогда до (иначе прерванный/вытесненный рендер оставит `current`
рассинхронизованным с DOM).

### 3. Инъекция времени и тика для детерминированных тестов

TECHNICAL_PLAN и SKILL требуют детерминированного контроля дедлайна без реальных
таймеров. Ввести инъектируемые зависимости с прод-дефолтами. Рекомендуемая форма —
одна функция конфигурации плюс приватный объект зависимостей:

```ts
interface SchedulerDeps {
  now: () => number;                 // дефолт: () => performance.now?.() ?? Date.now()
  scheduleTick: (cb: () => void) => void; // дефолт: MessageChannel-тик (фолбэк setTimeout(0))
  frameBudgetMs: number;             // дефолт: ~5
}

// Тестовый хук: переопределяет часть зависимостей и ВОЗВРАЩАЕТ функцию сброса к дефолтам.
export function __setSchedulerDeps(overrides: Partial<SchedulerDeps>): () => void
```

Требования и контракты:

- **`now`** — единственный источник времени в планировщике. `shouldYield()` сравнивает
  `now()` с сохранённым `deadline = renderStartNow + frameBudgetMs`. В тестах `now`
  возвращает управляемое значение (замыкание над `let clock`), так что тест эмулирует
  «превышение дедлайна», просто увеличивая `clock` между единицами работы — реальные
  таймеры не нужны.
- **`scheduleTick(cb)`** — «уступка потока»: планирует один асинхронный запуск `cb`
  (продолжение прерванной render-фазы). Прод-дефолт — `MessageChannel`
  (`port2.postMessage(null)` → обработчик `port1.onmessage` зовёт `cb`); фолбэк, если
  `MessageChannel` недоступен, — `setTimeout(cb, 0)`. `requestIdleCallback` можно
  упомянуть в комментарии как альтернативу для Idle-приоритета, но реализовывать его
  НЕ обязательно (TECHNICAL_PLAN даёт его лишь как фолбэк-вариант). **jsdom-оговорка:**
  `MessageChannel` в jsdom ненадёжен/асинхронен непредсказуемо — поэтому в тестах
  `scheduleTick` подменяется на **управляемый синхронный стаб** (складывает `cb` в
  массив/очередь; тест вызывает их вручную — «flush»), что делает разбиение на тики
  детерминированным и наблюдаемым. Именно ради этого `scheduleTick` инъектируем.
- **`frameBudgetMs`** — параметризуемый бюджет кадра. В тестах ставится маленьким или
  в паре с шаговым `now`, чтобы `shouldYield` срабатывал после заранее известного числа
  единиц работы.
- Дефолты должны работать в реальном браузере без инъекции; `__setSchedulerDeps`
  используется только тестами (двойное подчёркивание — маркер «внутреннее, не публичный
  контракт»). Не ре-экспортировать его из `index.ts`.

### 4. Work loop и `shouldYield`

Указатель `nextUnitOfWork` и текущий WIP-корень — **module-state в `scheduler.ts`**
(в Этапе 4 их сознательно вынесли из `fiber.ts` именно под это):

```ts
let nextUnitOfWork: Fiber | null = null;
let wipRoot: Fiber | null = null;   // корень текущего (возможно, недостроенного) рендера
```

Форма цикла (`workLoop`):

```
while (nextUnitOfWork !== null && !shouldYield()) {
  nextUnitOfWork = performUnitOfWork(nextUnitOfWork);
}
```

Развилки после выхода из цикла:

- **`nextUnitOfWork === null`** → render-фаза завершена. Синхронно, неделимо:
  `commitRoot(wipRoot)`; затем обновить `currentRoot`/`currentVNode` = только что
  закоммиченное; очистить `wipRoot`/`nextUnitOfWork` (= `null`); после этого, если в
  очереди есть ещё ожидающие обновления — начать следующий рендер (см. §5). Commit
  НЕ проверяет `shouldYield` — он атомарный.
- **`nextUnitOfWork !== null` и `shouldYield() === true`** → бюджет кадра исчерпан, но
  работа не закончена: уступить поток — `scheduleTick(() => workLoop())`, выйти. При
  следующем тике `workLoop` пересчитывает дедлайн от свежего `now()` и продолжает с
  сохранённого `nextUnitOfWork`. Обязательно **пересчитывать `deadline` в начале каждого
  входа в `workLoop`** (renderStartNow = now() на входе), иначе первый же тик решит, что
  дедлайн уже прошёл.

`shouldYield()` — приватная: `return deps.now() >= deadline;`, где `deadline` — module-var,
переустанавливаемая на входе в `workLoop`.

### 5. Очередь приоритетов и вытеснение

**Очередь ожидающих обновлений.** Хранить module-level, напр.
`let pending: Array<{ container: Element; vnode: VNode | null; priority: Priority }> = []`.
Каждый `scheduleWork` кладёт запись в очередь и запускает «пинок» планировщика
(`ensureScheduled()` — если сейчас ничего не идёт, начать; если идёт — см. вытеснение).
«Приоритетнее» = меньшее число `Priority`. Из очереди для старта рендера выбирается запись
с наивысшим приоритетом (наименьшим числом); при равенстве — FIFO (устойчивый выбор,
чтобы порядок был предсказуем для тестов). Полноценная приоритетная куча не нужна —
линейный выбор минимума по короткой очереди достаточен и проще.

**Начало рендера из очереди** (`startRender(entry)`):
- запомнить `activePriority = entry.priority`;
- `wipRoot = createWorkInProgress(entry.container, prevVNodeFor(entry.container), entry.vnode)`;
- `nextUnitOfWork = wipRoot`;
- убрать запись из `pending`;
- запустить `workLoop` (напрямую или через первый тик — см. ниже про синхронность).

**Вытеснение (preemption).** Если во время идущего рендера приходит `scheduleWork` с
приоритетом **строго выше** `activePriority` (меньшее число), текущий WIP отбрасывается
и рендер перезапускается с более приоритетным корнем:
- «отбросить» технически = обнулить `nextUnitOfWork`/`wipRoot`, ничего не коммитя (DOM не
  тронут — render-фаза его не мутирует, поэтому откат бесплатен и безопасен; в этом и был
  смысл разделения фаз);
- **важно:** `currentRoot`/`currentVNode` НЕ трогаются при отбросе (они = закоммиченный
  DOM), поэтому новый `createWorkInProgress` возьмёт корректный prev;
- затем `startRender` для более приоритетной записи. Прерванная запись, если её ещё нужно
  применить, остаётся в `pending` и будет подхвачена после (либо — проще для учебного
  объёма — считать, что более приоритетное обновление того же контейнера **замещает**
  фоновое: тогда при вытеснении фоновую запись того же контейнера из `pending` убрать.
  Выбрать поведение осознанно и покрыть тестом; замещение того же контейнера — ожидаемая
  React-подобная семантика «свежий стейт побеждает»).
- обновление с приоритетом **не выше** идущего — просто остаётся в `pending` и обработается
  после завершения текущего рендера (не вытесняет).

**Защита от stale-тика.** Отложенный `scheduleTick`-callback может сработать уже после
того, как рендер был вытеснен/завершён. `workLoop` должен быть идемпотентен к этому:
в начале проверять `if (nextUnitOfWork === null) return;` (или сверять сохранённый при
планировании тика `wipRoot` с текущим и выходить при расхождении). Достаточно проверки
`nextUnitOfWork === null` на входе — вытеснение обнуляет старый указатель и ставит новый,
а stale-тик, увидев чужой/сброшенный указатель, безопасно выйдет либо продолжит уже
актуальный рендер (оба исхода корректны, т.к. указатель — единый источник истины).

### 6. render vs commit — разнесение фаз

- **render** (прерываемая): всё, что делает `workLoop`/`performUnitOfWork` — строит WIP,
  размечает effect-tags, DOM не трогает. Может быть прервана `shouldYield` и возобновлена;
  может быть выброшена целиком при вытеснении.
- **commit** (`commitRoot`, синхронная неделимая): вызывается ровно один раз, когда
  `nextUnitOfWork` дошёл до `null`. Не проверяет дедлайн, не уступает поток, не прерывается.
  Только после успешного commit меняются `currentRoot`/`currentVNode`.

### Синхронность первого прохода — решить и фиксировать

Для тестируемости и простоты: `scheduleWork` **не** обязан быть полностью асинхронным.
Допустимо (и рекомендуется) запускать первый `workLoop` синхронно в рамках вызова
`scheduleWork`/`ensureScheduled`, а асинхронность возникает только когда `shouldYield`
разрывает работу на тики. Это делает короткие рендеры (влезающие в один бюджет) полностью
синхронными — их DOM готов сразу после `scheduleWork`, что удобно для jsdom-тестов
итогового дерева. Длинные рендеры (тест сдвигает `now` за дедлайн) разбиваются на тики,
наблюдаемые через управляемый `scheduleTick`-стаб. Зафиксировать это поведение
комментарием в коде.

## Критерий готовности (DoD)

- `npx tsc --noEmit` чисто; `npm test` зелёный; новый код покрыт тестами на **итоговом
  DOM-дереве** (jsdom), прерывания/дедлайн — детерминированно через инъекцию.
- Заглушка `scheduleWork` заменена рабочей реализацией; `TODO(Этап 5)` снят.
- Длинный рендер не выполняется одним синхронным проходом: при узком бюджете он разбивается
  минимум на 2 тика, и это наблюдаемо в тесте.
- Приоритеты соблюдаются: высокоприоритетное обновление применяется (коммитится) раньше
  ожидающего фонового; вытеснение идущего низкоприоритетного рендера работает.
- Итоговый DOM после любого числа прерываний/вытеснений идентичен результату синхронного
  `reconcile`/`render` для той же пары деревьев.
- Публичная сигнатура `scheduleWork(container, nextVNode, priority?)` отражена; `index.ts`
  в порядке (без лишних новых публичных символов).

## Тест-кейсы (`src/scheduler.test.ts`)

Стиль — как в проекте: где можно, утверждать на итоговом DOM через jsdom; прерывания и
дедлайн — детерминированно, через инъекцию `now`/`scheduleTick`/`frameBudgetMs`
(`__setSchedulerDeps`, с обязательным сбросом к дефолтам в `afterEach`). Использовать
`h`/`createElement` для построения деревьев. Список расширяет контур TECHNICAL_PLAN,
не заменяет его:

1. **Первый mount через scheduler.** `scheduleWork(container, tree, Normal)` с бюджетом,
   вмещающим весь рендер (один тик) → после (синхронного) завершения `container.innerHTML`
   равен результату `render(tree, container2)`.
2. **Re-render / update.** Второй `scheduleWork` тем же контейнером с изменённым деревом →
   DOM обновлён, идентичность неизменных узлов сохранена (сравнить node-identity до/после,
   как в reconciler-тестах) — доказывает, что prev взят из `currentRoot`.
3. **Размонтирование.** `scheduleWork(container, null, Normal)` после mount → корень удалён
   из DOM.
4. **Длинный рендер бьётся на несколько тиков.** Инъектировать шаговый `now` (растёт на
   каждый unit) + маленький `frameBudgetMs`, чтобы `shouldYield` срабатывал; `scheduleTick`
   — управляемый стаб (собирает callbacks). Утверждать: после первого синхронного куска
   DOM ещё НЕ полон / рендер не завершён (число накопленных тиков ≥ 1), после ручного flush
   всех тиков DOM полон и равен синхронному эталону.
5. **DOM не трогается до commit при прерывании.** На середине прерванного (не доведённого до
   flush) длинного рендера `container.innerHTML` не отражает новое дерево (render-фаза DOM
   не мутирует) — прямая проверка неделимости commit.
6. **Приоритет: высокий применяется раньше фонового.** Поставить `Normal`-обновление, затем
   `UserBlocking`/`Immediate` до того, как фоновое закоммитилось (контролируя тики) →
   первым в DOM оказывается высокоприоритетный результат.
7. **Вытеснение идущего рендера.** Начать длинный `Normal`-рендер (прерван на тике), затем
   `scheduleWork` с `Immediate` тем же контейнером → текущий WIP выброшен, высокоприоритетное
   дерево коммитится; итоговый DOM = высокоприоритетное дерево (и, по выбранной семантике
   §5, фоновое либо замещено, либо применяется после — проверить выбранный вариант явно).
8. **Не-вытесняющее обновление ждёт своей очереди.** Обновление с приоритетом не выше
   идущего не прерывает текущий рендер, а применяется после него; итоговый DOM отражает оба
   в корректном порядке.
9. **Порядок при равном приоритете — FIFO.** Два `Normal`-обновления в очереди применяются
   в порядке постановки.
10. **Идемпотентность stale-тика.** Смоделировать срабатывание отложенного тика уже после
    завершения/вытеснения рендера (вызвать собранный callback повторно) → без ошибок, DOM
    не портится.
11. **Эквивалентность синхронной версии (сквозной инвариант).** Для нескольких пар
    prev/next деревьев результат прогонки через scheduler (с прерываниями) побайтово равен
    результату синхронного `reconcile` на отдельном контейнере — прямое подтверждение DoD
    «результат идентичен синхронной версии».

`afterEach` обязателен: сбросить `__setSchedulerDeps` к дефолтам и обнулить module-state
планировщика (если не самоочищается между тестами — предусмотреть внутренний reset,
например переиспользовать сброс, возвращаемый `__setSchedulerDeps`, плюс явную очистку
`pending`/`currentRoot` при смене контейнера).

## Замечания для исполнителя

- Держать реализацию плоской и учебной: линейный выбор минимума в очереди, `enum Priority`
  как есть, никакой lane-модели.
- Единственный источник времени — инъектируемый `now`; ни `Date.now()`/`performance.now()`,
  ни реальные `setTimeout` не вызывать напрямую в логике (только внутри прод-дефолтов
  зависимостей).
- Не мутировать DOM нигде в render-фазе — весь DOM-выход только через `commitRoot`. Это то,
  что делает вытеснение бесплатным и корректным.
- `currentRoot`/`currentVNode` обновлять строго после `commitRoot`, атомарно, парой.
- Комментарии в коде — на английском (конвенция проекта); JSDoc в стиле соседних модулей
  `fiber.ts`/`reconciler.ts` (кратко объяснять «почему», а не только «что»).
